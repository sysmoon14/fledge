# The Fledge page in the Nest's settings

Recovery reads the device's `nlclient`, discovers its native UI addresses and
C++ object layouts, then links the embedded Fledge ARM object **in memory**.
The finished GUI and CLI require no Python, GCC, clang, LLVM linker, pip,
network access, or installed disassembly library to patch the screen.
The object is compiled once with the firmware when building the app.

Rust discovery incorporates research commit `aa5f304` from `imx6-stuff`: ELF
imports, screen registrations, ARM call graphs and address-independent
instruction fingerprints. Capstone's ARM decoder is statically linked.
The three audited ABI shapes (2025 gen3, 2019 gen3 and gen2) remain supported;
this does not infer arbitrary C++ semantics. Unsupported ELF layouts,
unknown instruction shapes, missing imports or unsupported relocations fail
before device writes. No firmware hash selects native addresses.

The home screen has a **192×192 Fledge icon**, the line “Fledge” with the
version of the app that patched the unit (`/etc/unfr0zen/version`), and Matter,
Zigbee, Doom and Done ring choices. Pages open at the top; status updates
preserve the viewport unless pairing completes. The larger QR has 10px of extra spacing above
its manual code. Matter, Zigbee and Doom choices appear only for enabled integrations. nestlocal
publishes its actual configured feature flags, independently of radio/service
readiness. Before it starts, the screen reads its installed options (including
the device override). With none enabled, the only choice is Done. **Doom** asks nestlocal to launch
the game, which takes the screen until it quits.

Matter displays a QR and manual pairing code generated by rs-matter from
the configured passcode/discriminator, plus live commissioning status.
**Enable pairing** asks whether to forget all Matter controllers and pair again.
**Forget and pair** removes their saved credentials and active sessions before
opening a basic commissioning window for up to 15 minutes, with an animated
activity indicator. Back cancels the confirmation without sending a request.
Once confirmed, forgetting cannot be undone: a failed or cancelled new pairing
does not restore the old controllers. Wi-Fi and Zigbee settings are retained.
An in-flight commissioning attempt rolls back before its credentials are removed.
The confirmed action uses `matter-reset.request`; legacy `matter.request` callers
retain their non-destructive replacement behavior until commissioning succeeds.
Initial enrollment opens commissioning automatically; the Matter screen shows
Ready to pair above the QR/code and offers Back. Completion switches to a
compact Paired status with Enable pairing and Back, resetting the viewport so
the result is visible without turning the ring. The active page polls every
250 ms and also recognizes completion when the open window falls between polls.
Paired thermostats offer Enable pairing when their window is closed to replace
the controller. Controllers can also remove their own pairing. The status text is separated from the manual code by a blank line.

Zigbee shows network/activity status. **Enable pairing** asks for confirmation
before leaving an existing network and forgetting its saved credentials. Enable permit
joining on the coordinator first. The menu attempt has a 30-second deadline
covering scanning and joining, with seconds remaining. Timeout stops further
automatic attempts until another Enable pairing request. Radio operations
finish at their normal command/wait boundaries. Back leaves the page; it
does not cancel an already sent request. nestlocal does not watch the ring;
holding it no longer starts Zigbee pairing.
While an activity page is visible, stock user-activity notifications keep the
display and device awake: for the open Matter window, or at most 30 seconds
for Zigbee. Back or completion stops those notifications and restores normal inactivity behavior.
The Fledge page is at settings-menu index 1, after the thermostat/Back entry at 0.
Its carousel tile displays the glyph above FLEDGE.
The other items retain their order.

## Screen hand-over

The patch also routes nlclient's one `eglSwapBuffers` call (discovered as the
`swap_call_slot` anchor) through `custom_swap`. While the process whose pid is
in `/var/run/unfr0zen/screen.owner` is alive, nlclient keeps running and
drawing but presents nothing, so that process owns the display. The check is
live (`kill(pid, 0)` on every frame), so the display returns to nlclient the
moment the owner exits or dies; a stale file does nothing.

nestlocal's home screen cards (`crates/nestlocal/src/ui/`) use this. With
cards from Home Assistant (the Fledge integration, sysmoon14/fledge-homeassistant),
waking the unit shows the device chooser: the thermostat among the cards,
zoomed out (or the device Fledge was told to wake to). Turning browses,
pressing opens; the thermostat hands the ring back to nlclient, and choosing
Back in nlclient's menu returns to the chooser. While a card shows, a thread
inside nlclient keeps its display awake; no ring input is ever injected.

The UI may hold the display at rest too, showing black or its glance while
nlclient's own timing (Farsight, wake on approach, the dark-room check) puts
the display out: it leaves `/var/run/unfr0zen/screen.rest` and the thread
stops keeping the display lit. An owner that writes `pid beat` must change the
beat within 5 s of the thread running, or its file is moved aside and nlclient
presents again, so a hung UI can't freeze the screen. The thread leaves
`/var/run/unfr0zen/keeper.rests` to say this build knows both; without it,
nestlocal hands the display back at rest as before.
Without cards, or while nlclient is stopped (Doom), nothing is held and the
unit behaves as stock.

### What nlclient shows

nlclient reports every change of its view, its screen and a screen's active
layer to its own telemetry, through one function (the `UiDisplayChange`
event: what changed and the new thing's name). Discovery finds that function
by the event's name and its `nlLogEvent` call, and the patch routes each of
its direct calls and tail calls through `custom_ui_change`, which keeps the
latest name of each thing in `/var/run/unfr0zen/nlclient.state` (written
whole and renamed into place) before reporting as before:

```text
6898 26
current screen	temperature
current view	thermostatview
active layer (nlTempScreen)	selectorlayer
```

The first line is nlclient's pid and its count of reports; the rest is one
line per thing, tab-separated, the latest last. On a gen 3 (2025 build):
`current view` is `thermostatview` (the home dial and its menu) or
`settingsview` (Settings, whose tiles are `current screen`); in the
thermostat, nlTempScreen's active layer is `temperaturesliderlayer` (the dial,
heating or off) or `selectorlayer` (the menu). Coming back from Settings
reports only the view: the thermostat opens on its dial.

nestlocal's UI reads this to know when nlclient's home dial, its menu or its
Settings show (Back in the menu, Done in Settings). A file whose pid is not a
running nlclient is ignored, as is its absence (a patch from before this, or
a build where the report isn't found, which is patched without it): then the
UI reads nlclient's pixels as before. Selection within a menu isn't reported,
so opening Settings from the cards still checks Settings is chosen by its
pixels before pressing.

## Runtime and build requirements

Run the packaged app or CLI. No screen-patching tools need to be installed on
the user's machine. A dry run discovers, links and reports changes without
writing to the device. Patching, hash checks and undo-journal generation all
happen in memory, without launching an external process or extracting source
into a temporary directory.

Developers still need the ordinary firmware/app build toolchain.
`utils/build-firmware.sh` compiles `build/custom-screen.o` with ARM clang;
`fledge-host` embeds it into both front ends. Cargo builds the bundled static
Capstone decoder with a C compiler, as it builds other native dependencies.
These compilers are build requirements only. There is no runtime compilation.
The decoder enables only the ARM architecture.

## Applying and upgrading

`src/custom_screen.c` uses stock screen, text, image and ring APIs;
`src/custom_flow.h` contains firmware-independent navigation. API addresses
and vtable layouts are discovered from the input ELF and supplied as absolute
symbols to the in-memory Rust linker. Mutable state lives on
the heap; the injected PT_LOAD segment is read/execute only.

Recovery verifies the input SHA256, stages a copy, applies the freshly built
changes, verifies the complete output SHA256 and atomically renames the copy.
The generated **undo journal** records changed original bytes, injected bytes,
and both hashes. It is generated per device, never used as a prebuilt shortcut:

- `/nestlabs/share/images/G_unfr0zen_192px.png`
- `/etc/unfr0zen/nlclient.undo.gz`
- `/etc/unfr0zen/nlclient.original` — full original executable, root-only (mode 600)

Recovery creates and verifies the full original backup before replacing
`nlclient`. Subsequent runs preserve it without rewriting it. For devices
patched by an earlier version, recovery reconstructs the original using the
undo journal and saves that full copy. An existing backup with a different
hash stops patching and is left untouched.

On subsequent runs, the journal reconstructs the original executable on the
host before discovery and linking. This supports upgrades without a
separate stock download. An unchanged build is idempotent.

nestlocal and the screen communicate through root-only files in
`/var/run/unfr0zen`. nestlocal atomically publishes `matter.png`, `matter.code`
and protocol `.status` files, and `features` (a digit: Matter 1, Zigbee 2,
Doom 4); clicks atomically publish a `.request` (`matter`, `zigbee` or `doom`)
consumed by its worker. Startup removes stale requests and credentials.
Disabled/unavailable services report an error on action. Native timer events
refresh status once per second while the screen is open, even with the ring idle;
pairing activity animates four times per second.

## Build locally and verify

The CLI can patch a local stock executable without touching USB:

```sh
fledge nlclient /path/to/stock/nlclient --out build/nlclient-screen
```

It writes the executable, `.json` discovery/build manifest and `.undo.gz`
journal. This uses the same embedded object and Rust builder as recovery.
Input and output paths must be distinct. The object has no mutable globals
or dynamic relocations. The linker reproduces `ld.lld -O0` section layout,
string order and ARM ABS32/REL32/CALL/JUMP24 relocations, and rejects any
unknown allocated section or relocation. It does not synthesize veneers.

```sh
cargo test -p fledge-core -p fledge-host -p fledge-cli
NLCLIENT_REQUIRE_GOLDENS=1 cargo test -p fledge-core --test nlclient_golden
NLCLIENT_STOCK="$PWD/.work/firmware/nlclient-gen3-2025" \
  cargo test -p fledge-core native_screen_patch_is_automatic -- --ignored
```

Goldens from all three untouched dumps pin discovery, native API, planned
patch, linked payload/symbols, output and decompressed undo journal against
the independent Python/lld reference. They contain addresses and hashes,
never firmware. See [tests/README.md](tests/README.md) for sample provenance,
strict mode, toolchain details and the optional same-object `ld.lld` check.
Private samples are kept under `.work/firmware/` or `NLCLIENT_FIRMWARE_DIR`.
Tests also cover moved ELF addresses, corrupted ABI rejection, unsupported
relocations, patch/undo round trips and recovery dry run/idempotence/upgrades,
including interrupted executable or journal writes.

To exercise the builder directly during development without the host/USB
crate, use the Rust example:

```sh
cargo run -p fledge-core --bin nlclient -- \
  .work/firmware/nlclient-gen3-2025 build/custom-screen.o build/nlclient-screen
```

QEMU testing uses a matching isolated NAND; the walkthrough is in
`imx6-stuff/nlclient/docs/CUSTOM-LOGIC.md`. Physical QR scanning, Matter
commissioning and a Zigbee radio join remain device acceptance checks.

## Undo locally

The full original is available directly at `/etc/unfr0zen/nlclient.original`.
Restore it to `/nestlabs/sbin/nlclient` with the executable's original ownership
and permissions (normally root-owned, mode 755), while nlclient is stopped.

Alternatively, use the undo journal:

Copy the executable and `/etc/unfr0zen/nlclient.undo.gz` from the device.
Reconstruct stock on the host:

```sh
fledge nlclient nlclient-from-unit --undo nlclient.undo.gz --out nlclient-stock
```

Both hashes are checked. Install stock with nlclient stopped, then restart
it. A later recovery rebuilds the Fledge screen from that executable.
